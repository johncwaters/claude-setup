Agent-Docs Eval Harness for PostHog

Measure how well coding agents complete real PostHog tasks under different context regimes, publish the findings, keep the suite running nightly.
Plan drafted 2026-07-30. Lives at evals/ in this repo. Application project for the PostHog Context Engineer role.

Thesis

PostHog's Context Engineer role is about making a product legible to AI agents, not just humans. The honest way to evaluate that legibility is to hand real tasks to a real coding agent under controlled context conditions and score the outcomes programmatically. This harness does exactly that, instruments every run with PostHog's own LLM analytics, and turns the results into a public writeup plus upstream doc-fix PRs.

Constraints already decided: lives inside this repo at evals/, no always-on session telemetry (eval runs log to PostHog, daily Claude usage does not), no work-related content.

Deliverables

  • Harness: evals/ with task specs, runner, scorers, and results. Reusable: target docs and regimes are config, not code.
  • Data: every run captured as PostHog events and LLM traces in a personal PostHog project; dashboards are the results section.
  • Writeup: which context regime wins per task class, where docs fail agents, token cost per success, with failure examples. Published as a page in docs/ plus a blog-style post.
  • Upstream contributions: doc-gap findings filed as issues or PRs against posthog.com docs.
  • Regression gate: nightly scheduled run so doc drift shows up as a score drop, not a one-time snapshot.

Architecture

evals/
  README.md              what this is, how to run, results summary
  config.yml             regimes, models, trial counts, budget caps
  tasks/
    install-nextjs/      task.yml + workspace template + checks.py
    hogql-funnel/
    feature-flag-rollout/
    ...
  runner/
    run.py               orchestrates: workspace -> agent -> checks -> record
    regimes.py           context regime assembly (none, llms.txt, mcp, bundle)
    scoring.py           invokes task checks, normalizes verdicts
    posthog_capture.py   events + $ai_* trace ingestion
    journal.py           typed per-run JSONL journal, resume support
  bundles/               hand-built context bundles (the "context engineering")
  results/               per-run JSON + roll-up summary (tracked)

Run flow: for each (task, regime, trial): create throwaway workspace from template, assemble context per regime, spawn headless Claude Code (claude -p --output-format json, model and max-turns pinned from config), run the task's programmatic checks, write journal entry, emit PostHog events. The runner is plain Python, no framework.

Precedent in this repo: compiled-commit/bench/ already does fixtures, judge, and scored results for the commit runner. Same discipline, second harness, and the journal/resume pattern is carried over.

Context regimes

RegimeWhat the agent getsWhat it isolates
noneTask prompt only, web access offBaseline: model training data alone
llms-txtposthog.com llms.txt content injected as contextValue of PostHog's existing agent-facing docs
mcpPostHog MCP server connected, no doc injectionValue of live tool access vs static docs
bundleHand-built task-scoped context bundle from bundles/Ceiling: what curated context engineering buys

The bundle regime is the actual context-engineering work product: token-budgeted, task-scoped extractions from PostHog docs. The writeup's core claim is the measured gap between bundle and the others.

Task suite (12 tasks, 4 classes)

ClassTasksGround-truth check (programmatic, no LLM judge)
SDK installNext.js app + custom event; Python backend capture; React Native screen trackingApp builds; expected event with expected properties arrives in a throwaway PostHog project, verified via API poll
HogQLFunnel query; retention query; error-tracking aggregationQuery executes against a seeded project and returns known-correct rows
Product configFeature flag with 50% rollout; survey targeting a cohort; insight + dashboard creationObject exists via API with exact expected shape (rollout %, filters, series)
IntegrationCapture LLM trace via ai SDK; batch export config; reverse proxy setup snippetTrace/event arrives; config validates against API; snippet passes a lint harness

Seeded project: a fixture script populates a dedicated PostHog project with deterministic demo events so HogQL tasks have known-correct answers. Each task ships checks.py returning pass/fail plus failure reason codes.

Measurement and instrumentation

Per run, recorded to journal and PostHog:

  • eval_run_completed event: task, regime, trial, pass/fail, failure reason code, wall time, turns used
  • Token accounting from claude -p JSON usage (same accounting scheme as compiled-commit bench): gross, non-cached, output, cost USD
  • LLM trace via PostHog AI observability ($ai_generation family) so individual failures are inspectable in-product
  • Hallucination flags: checks record wrong-API usage distinctly from build failures (e.g. invented SDK method vs missing env var)

Dashboards: pass rate by regime, pass rate by task class, cost per success, failure reason breakdown, nightly trend line. Built in the same PostHog project, linked from the writeup.

Phases

P1: Skeleton (2-3 evenings)

Runner + 3 install-class tasks + none/llms-txt regimes

Prove the loop end to end: workspace, headless spawn, event-arrival check, journal, one PostHog event per run. Exit: 3 tasks scored under 2 regimes, results reproducible.

P2: Full matrix (1 week)

All 12 tasks, all 4 regimes, 2 trials each

Add MCP regime, build the context bundles (the real work), seed fixture project for HogQL tasks. Exit: 96-run matrix complete with cost accounting.

P3: Live system (2-3 evenings)

Dashboards + nightly schedule

PostHog dashboards, Windows scheduled task running a nightly subset (1 trial, cheapest model tier that still discriminates), failure alerting via PostHog. Exit: score drop on doc drift is visible without manual runs.

P4: Publish (1 week, overlaps P3)

Writeup + upstream findings

Analysis writeup with data, per-gap doc findings filed upstream, README polish, application submitted linking repo + writeup + live dashboard snapshot.

Budget and risk

RiskMitigation
Token cost blowoutPinned model (sonnet), max-turns cap, per-run and per-batch USD caps in config; runner halts batch at cap. Estimate: 96 runs at roughly $0.15-0.50 each, order of $30, spread over nights.
Flaky scoringNo LLM judges anywhere in the pass/fail path. Ground truth is API-verified state. 2 trials per cell; disagreement is itself reported data, not noise to hide.
PostHog free-tier limitsEvent volume is tiny (hundreds/month). Throwaway capture projects reset per batch via fixture script.
llms.txt or docs change mid-experimentRegime inputs are snapshotted per batch with content hashes; every result row records which snapshot it ran against.
Agent nondeterminism inflating claimsReport confidence honestly: small-n caveats in the writeup, per-cell trial counts shown, raw journals published.
Secrets in a public repoAPI keys via env only; evals/ inherits repo .gitignore discipline; journals scrubbed of keys before tracking results.

Definition of done

  • 96-run matrix complete with published journals and cost accounting
  • Nightly run live for at least a week before application submission, trend visible in dashboard
  • Writeup published: regime comparison, failure taxonomy, at least 3 concrete doc-gap findings filed upstream
  • Repo public, harness reproducible by a stranger with their own keys (README-verified)
  • Zero secrets, zero work references (re-run the pre-publication scan before submission)
