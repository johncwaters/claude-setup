Agent-Docs Eval Harness for PostHog

Measure how well coding agents complete real PostHog tasks under different context regimes, publish the findings, raise n with on-demand batch reruns.
Plan drafted 2026-07-30. Lives at evals/ in this repo. Application project for the PostHog Context Engineer role. No timeline: steps complete in order, at working pace.

Thesis

PostHog's Context Engineer role is about making a product legible to AI agents, not just humans. The honest way to evaluate that legibility is to hand real tasks to a real coding agent under controlled context conditions and score the outcomes programmatically. This harness does exactly that, instruments every run with PostHog's own LLM analytics, and turns the results into a public writeup plus upstream doc-fix PRs.

Constraints already decided: lives inside this repo at evals/, no always-on session telemetry (eval runs log to PostHog, daily Claude usage does not), no day-job content. Every eval task is real: sourced from actual work on my own shipping products (card-harbor, keeplings), never invented scenarios.

Deliverables

  • Harness: evals/ with task specs, runner, scorers, and results. Reusable: target docs and regimes are config, not code.
  • Data: every run captured as PostHog events and LLM traces in a personal PostHog project; dashboards are the results section.
  • Writeup: which context regime wins per task class, where docs fail agents, token cost per success, with failure examples. Published as a page in docs/ plus a blog-style post.
  • Upstream contributions: doc-gap findings filed as issues or PRs against posthog.com docs.
  • Regression gate: on-demand batch reruns (journal resume makes them cheap) so doc drift shows up as a score drop between batches, not a one-time snapshot.

Architecture

evals/
  README.md              what this is, how to run, results summary
  config.yml             regimes, models, trial counts, budget caps
  tasks/
    ch-renderer-capture/   task.yml + repo ref + pinned commit + checks.py
    ch-error-sourcemaps/
    kp-release-impact/
    ...                    (ch- = card-harbor prospective, kp- = keeplings retrospective)
  runner/
    run.py               orchestrates: workspace -> agent -> checks -> record
    regimes.py           context regime assembly (none, llms.txt, mcp, bundle)
    scoring.py           invokes task checks, normalizes verdicts
    posthog_capture.py   events + $ai_* trace ingestion
    journal.py           typed per-run JSONL journal, resume support
  bundles/               hand-built context bundles (the "context engineering")
  results/               per-run JSON + roll-up summary (tracked)

Run flow: for each (task, regime, trial): create a throwaway git worktree of the task's repo at its pinned commit, assemble context per regime, spawn headless Claude Code (claude -p --output-format json, model and max-turns pinned from config, subscription auth), run the task's programmatic checks, write journal entry, emit PostHog events, discard the worktree. The runner is plain Python, no framework. Single-model scope: config pins one model, so results are claims about context regimes on that model, and the writeup states that scope explicitly rather than implying generality.

Precedent in this repo: compiled-commit/bench/ already does fixtures, judge, and scored results for the commit runner. Same discipline, second harness, and the journal/resume pattern is carried over.

Context regimes

RegimeWhat the agent getsWhat it isolates
noneTask prompt only, web access offBaseline: model training data alone
llms-txtposthog.com llms.txt snapshot injected (verified: a ~330 KB link index of .md doc URLs; llms-full.txt 404s), plus WebFetch scoped to posthog.com only, since following the index's links is the file's designed useValue of PostHog's existing agent-facing docs pathway
mcpPostHog MCP server connected, no doc injection; the agent authenticates with a project-restricted personal API key carrying read-only scopes, plus the MCP server's documented readonly session flag and project-pin header, so keeplings production is read-only and writes land only in the scratch projectValue of live tool access vs static docs
bundleHand-built task-scoped context bundle from bundles/Ceiling: what curated context engineering buys

WebSearch is off in every regime. WebFetch is off everywhere except llms-txt, where it is domain-scoped to posthog.com because llms.txt is an index whose designed use is link-following; unrestricted browsing in any regime would collapse the comparison. One known constant: prospective worktrees carry the product repo's own CLAUDE.md/AGENTS.md into every regime, so none is a repo-context baseline, not zero-context; it is identical across regimes and stated as such in the writeup. The bundle regime is the actual context-engineering work product: token-budgeted, task-scoped extractions from PostHog docs. The writeup's core claim is the measured gap between bundle and the others.

Bundle blinding protocol

The bundle-vs-rest gap is only credible if a bundle cannot encode the answer. Rules, enforced per task:

  • Bundles are built exclusively from public PostHog docs. Never from the task's reference implementation, my landed code, or any agent run output.
  • For prospective card-harbor tasks, the bundle is authored and frozen before the reference implementation lands, so it cannot be answer-scoped even accidentally.
  • Every bundle is content-hashed and frozen before its first scored run; every result row records the hash it ran against.
  • No edits in response to observed results. A post-freeze edit creates a new bundle version, and all prior rows for that cell are discarded from the matrix, not mixed.

Task sourcing: real work only

Tasks come from two live products, both mine, both instrumented (or being instrumented) with PostHog. No synthetic scenarios; every task is something I actually needed done.

Each task ships checks.py returning pass/fail plus failure reason codes. Target is still a ~12-task suite across install/instrumentation, HogQL/analysis, error tracking, and product config classes; the classes survive, the content is now sourced from real work.

Capture loop (the daily-workflow wiring)

A small evals capture command snapshots a just-completed real task into evals/tasks/: the prompt as actually given, the repo commit before the work, the landed outcome, and generated check stubs to fill in. Completing real PostHog work on my products grows the eval suite as a side effect; the suite is a work log, not a test-authoring project. Retired tasks stay in the suite as regression rows since docs can break yesterday's answer.

Measurement and instrumentation

Per run, recorded to journal and PostHog:

  • eval_run_completed event: task, regime, trial, pass/fail, failure reason code, wall time, turns used
  • Token accounting from claude -p JSON usage (same accounting scheme as compiled-commit bench): gross, non-cached, output, cost USD
  • LLM trace via PostHog AI observability ($ai_generation family) so individual failures are inspectable in-product
  • Hallucination flags: checks record wrong-API usage distinctly from build failures (e.g. invented SDK method vs missing env var)
  • A distinct check-infra failure code for harness-side faults (ingestion poll timeout, API errors, rate limits): these rows are excluded from regime pass rates and rerun, so infrastructure lag never counts against a regime

Dashboards: pass rate by regime, pass rate by task class, cost per success, failure reason breakdown, per-batch trend line. Built in the same PostHog project, linked from the writeup.

Build order

1. Intake first

evals capture command + first 6 real tasks

Capture comes before the runner because daily task volume is the asset: snapshot 3 card-harbor integration slices (prospective) and 3 keeplings analytics questions with verified answers (retrospective). From here, every day of normal product work adds tasks at near-zero cost. Critical path: a prospective task is scorable only after its reference implementation lands, so that half of the suite grows at product-work pace; retrospective keeplings tasks have no such gate and can fill in immediately.

2. Runner core

Worktree spawn, checks, journal, PostHog events; score under none + bundle

Prove the loop end to end on the captured tasks with the two regimes that carry the core claim (baseline vs curated context). Exit: 6 real tasks scored, reproducible.

3. Full regimes + on-demand batches

llms-txt and mcp regimes; detached batch runs fill the matrix

Fast-tracked: batches launch on demand (detached from the session) rather than on a nightly schedule, with rate-limit backoff and journal resume. Repeat batches raise n per cell by appending trials to the same journal. Exit: full matrix filled at n≥4.

4. Dashboards + writeup

Then rolling: capture daily, batches accumulate on demand, writeup hardens

Dashboards from the first complete matrix, writeup drafted against real numbers, doc-gap findings filed upstream as they surface. Submission gate (fast-tracked): full matrix at n≥4 with stable pass rates across two independent batches, replacing the original week-of-nightly-trend requirement.

Budget and risk

RiskMitigation
Usage-limit exhaustionRuns ride the Claude subscription (headless CLI with subscription login, no API key set), so the constraint is rate limits, not dollars. Caps in config are runs-per-batch and tokens; runner backs off and resumes on rate-limit errors via the journal. Batches run on demand while the limit is otherwise idle. total_cost_usd is still recorded and reported as API-equivalent pricing, labeled as such in the writeup.
Bundle answer leakageBlinding protocol (see Context regimes): bundles sourced from public docs only, content-hashed and frozen before the first scored run, prospective bundles authored before the reference implementation lands, and any post-freeze edit discards prior rows for that cell.
Flaky scoringNo LLM judges anywhere in the pass/fail path. Ground truth is API-verified state or a human-verified answer over a pinned time window. 2 trials per cell to prove the loop; follow-up batches then raise n, headline cells (none, bundle) first. Disagreement between trials is itself reported data, not noise to hide.
PostHog free-tier limitsEvent volume is well within free-tier limits. Scratch capture project for prospective tasks resets per batch; keeplings production data is read-only to the harness.
Suite bloat from high task volumeDaily work produces more captures than the matrix needs. The submission matrix is pinned at ~12 representative tasks across the four classes; further captures queue as regression rows for later batches, not matrix growth. Every capture beyond the pin is logged, not silently dropped.
Product data in public resultsPublished journals and results contain aggregates and pass/fail only; raw keeplings analytics stay in PostHog. Scrub pass runs before tracking results.
llms.txt or docs change mid-experimentRegime inputs are snapshotted per batch with content hashes; every result row records which snapshot it ran against. The pages the llms-txt regime fetches by following index links are live by design; the index snapshot hash plus run timestamp bound that drift.
Agent nondeterminism inflating claimsPass rates reported with Wilson score intervals and per-cell n shown; detecting a 10-point pass-rate difference with a two-proportion test at alpha 0.05 and power 0.90 needs roughly 100 trials per cell when comparing 90% against 80%, and several hundred when both rates sit near 50%, so batch accumulation targets the headline cells first and the writeup frames smaller-n comparisons as directional. Raw journals published.

Definition of done

  • Full matrix over the captured real-task suite complete, with published journals and token accounting
  • Full matrix at n≥4 with pass rates stable across two independent batches (fast-tracked from the original week-of-nightly-runs gate), trend visible in dashboard
  • Writeup published: regime comparison, failure taxonomy, at least 3 concrete doc-gap findings filed upstream
  • Repo public, harness reproducible by a stranger with their own keys (README-verified)
  • Zero secrets, zero work references (re-run the pre-publication scan before submission)
